# EmberMap

第五人格「加页手记」模式（噩梦难度）的地图识别/覆盖辅助工具：
截图游戏内地图（部分已探索）→ 识别是 13 个变体中的哪张、哪一层 → 求相似变换 → 对齐叠加完整手绘图与门位。

## 目录

- `draw-em/` — 手绘示意图，13 变体 × 3 层，含 `doors.json` 门位标注；用作**展示层**
- `game-em/` — 游戏内实拍拼图，与游戏内渲染同风格；用作**匹配层**（几何忠实，不可替换）
- `data/` — 项目自有元数据：变体命名与配对、楼层切分人工覆盖、门位（game 坐标系）
- `proto/` — Python 原型（掩码提取、楼层切分、匹配、评测、实机监测），算法准绳
- `em-core/` — 纯 Rust 匹配核心（无 OpenCV），语义与 proto/emlib.py 对齐，双实现校验
- `app/` — Tauri 2 应用（`app/bundle/` 为数据包，`proto/build_bundle.py` 生成）
- `build/` — Python 生成物（参考库、质检图、评测输出），不入库

## 应用

```bash
cd app/src-tauri && cargo run --release        # 开发运行
cd app && npx @tauri-apps/cli build            # 打发行包（dmg/nsis/deb/AppImage）
```

首次运行需授予屏幕录制权限（macOS：系统设置 → 隐私与安全性 → 屏幕录制）。

功能：抓游戏窗口自动识别 / 整层地图叠加（覆盖模式为透明点击穿透窗，
不挡操作、对抓屏隐形）/ 并排窗口模式 / 窗口置顶 / 叠加透明度 /
**手动锁定地图与楼层** / 全局热键 **⇧⌥M** 切换覆盖层、**⇧⌥R** 重新识别。

手动锁定（「锁定当前」按钮 + 地图下拉 + 楼层按钮）把匹配范围收窄到指定
变体/楼层：主界面之类的画面不会再被认成某张地图，楼层认错也能一键纠正，
候选从 39 条降到 3 条或 1 条，单帧耗时随之减半。

Android 端同样可用（模拟器验证，真机待测）：投屏取帧 + 悬浮窗叠加，
识别结果与桌面一致。构建：

```bash
export ANDROID_HOME=<sdk> NDK_HOME=<sdk>/ndk/<版本>
cd app && cargo tauri android build --target aarch64 --target x86_64 --apk
```

识别策略：首次识别慢而准（全库多尺度，多帧投票攒够证据才锁定，证据不足
宁可持续显示「识别中」）；锁定后仍每帧全库扫描，锁只作显示粘滞，
所以误判能在两帧内自我纠正。详见 `app/src-tauri/src/tracker.rs`。

排障：应用把每帧决策写到 stderr（耗时/相位/证据/分差/候选）；
`EM_DUMP=1` 额外把匹配器所见的裁剪图落到 `/tmp/em_panel.png`。

各平台实现方案（含 Windows 注意事项与 Android 悬浮窗方案）见
[docs/platforms.md](docs/platforms.md)。

一致性校验（Rust vs Python，两张真实截图）：

```bash
cd em-core && cargo run --release --example match_file -- ../app/bundle 你的截图.png
# --overlay <目录>：落盘「截图 + 参考掩码描边 + 手绘层 + 门位」的合成图，
#                   叠加错位这类几何问题看分数看不出来，看合成图一眼可辨
# --pin 变体id:楼层：模拟界面上的手动锁定（任一段可留空）
```

## 原型用法

```bash
python3 -m venv .venv && .venv/bin/pip install opencv-python-headless numpy pillow

.venv/bin/python proto/build_library.py   # game-em → build/library/（匹配参考库，39 楼层掩码）
.venv/bin/python proto/build_draw.py      # draw-em → build/library-draw/（展示层）
.venv/bin/python proto/pair.py            # 自动配对 draw↔game 变体
.venv/bin/python proto/map_doors.py       # 门位坐标映射到 game 坐标系
.venv/bin/python proto/synth_eval.py      # 合成"部分探索"查询做交叉评测
.venv/bin/python proto/match.py 截图.png --debug   # 匹配一张真实截图
```

## 算法

1. **结构掩码**：HSV 颜色分割提取可行走结构（走廊+房间），滤除水印/攻略线/文字；
2. **楼层切分**：腐蚀出楼层核心打断细水印桥 → 像素距离单链接聚类到 3 簇 → 像素按最近核心归属；
3. **匹配**：查询掩码对 39 个楼层做多尺度平移搜索（相似变换，无旋转），
   得分 = 0.6×前景命中率 + 0.4×背景命中率；粗筛全库后 top-5 精修重排。

## 验证历程

准确率是这个项目唯一的硬风险，所以验证分三级递进，每级都推翻过上一级的乐观结论——
记录在此，因为「哪些结论只在实验室成立」比结论本身更值得记住。

**一级·合成评测**（`proto/synth_eval.py`）：从参考库自身用测地生长合成
「部分探索」查询，350 条交叉匹配。结论见下表，接近满分。
局限：只证明了 13 个变体彼此可判别，没有触及真实渲染差异。

**二级·真实截图**：用户提供的两张游戏截图（Mac 客户端 2940×1846）。
颜色阈值零改动即通过，但暴露了合成评测碰不到的问题——游戏 UI 文字的色相
与走廊重叠（H≈105），**不裁剪地图面板就会把 UI 当结构**，得分从 0.84 掉到 0.61。

**三级·实机对局**：真正推翻假设的一级。逐个被日志抓出来的问题：

| 现象 | 真因 |
|---|---|
| 整个应用卡死 | Tauri 同步命令跑在主线程，每帧把 UI 冻住 2 秒 |
| 识别一错就一直错 | 「锁定后只匹配锁定变体」是自我确认陷阱，误锁永不纠正 |
| 永远停在「识别中」 | 尺度先验在两种分析分辨率间错配 2 倍；且每个无面板帧都清空投票 |
| 错误率偏高 | HUD 小地图仅 255×269，13 个变体挤在 0.845-0.857，**分差 0.000-0.006 等于随机**，而当时的逻辑会在 4 帧后强制锁定 |
| 抓到的不是游戏画面 | 抓的是整屏，切窗口时被其他窗口遮挡 → 改为直接抓游戏窗口 |

这些都不是算法问题，而是**工程与判定策略**问题——合成评测再高分也测不出来。
最终策略：证据不足宁可不锁（`MIN_FRAME_ADVANTAGE`），锁定后仍每帧全库扫描，
锁只作显示粘滞。

**测试素材为何不在仓库里**：那些截图是个人游戏画面，已从 git 历史中移除
（`test/` 已列入 `.gitignore`）。想自己复现精度对比，把截图放进 `test/` 后运行：

```bash
cargo run --release --example sweep -- app/bundle "test/你的截图.png:右中门1-2:1f"
```

CI 里的自动回归改用 `em-core/tests/synth_regression.rs`：从参考库自身合成查询，
断言匹配找回原条目且尺度可复原，不依赖任何外部图片。

## 合成评测（2026-08-27，350 条查询）

| 探索程度 | top-1 | top-2 | 对齐误差中位 |
|---|---|---|---|
| 开局（测地半径 150px） | 99.1% | 99.1% | 1.7px |
| 中期（350px） | 100% | 100% | 2.1px |
| 完整楼层 | 100% | 100% | 2.6px |

单次匹配约 2s（未优化 Python 原型；Rust 版 acquire 约 1.3-1.5s、跟踪约 0.8-0.9s）。
